# frame/join.h - DataFrame equi-join

## Overview

**Installation tier:** core (see README's [Installation tiers](../README.md#installation-tiers) policy) — a data-wrangling primitive over `DataFrame`, with no fitting procedure, the same tier as `frame/frame.h`/`frame/sql.h`.

`frame/join.h` joins two `DataFrame`s on one shared column name: `df_join(left, right, on, how)`. The algorithm - build a hash table over one side's key column once, probe it with every row of the other side, and for `JOIN_FULL` track which build-side rows a probe ever matched so the ones that never did can be appended afterward - is ported from real Polars source (`crates/polars-ops/src/frame/join/hash_join/single_keys_inner.rs`, `single_keys_left.rs`, `single_keys_outer.rs`, tag `py-1.38.1`), the same porting standard `frame/sql.h`'s `WHERE`/`GROUP BY` already follow for their own Polars-derived pieces. Above `JOIN_PARALLEL_MIN_N` combined rows, the build is additionally partitioned and both the build and the probe run multithreaded via OpenMP - see the Multithreading section below; this is also ported from Polars' actual technique in that same source. What is *not* ported is Polars' build-side-size heuristic (it builds over whichever relation is smaller, swapping the output tuple order back after) - `df_join` always builds over `right` regardless of which side is bigger - a pure performance concern left for future work (see Known limitations).

The hash table itself (`FrameHashTable`, `DirtyHash`, canonical NaN/-0.0 folding) is not new: it is the same table `frame/sql.h`'s `GROUP BY` already built and tested, extracted into `frame/frame.h` once `join.h` became a second caller — see that header's own comment on `FrameHashTable` for the two real bugs (top-bits-vs-low-bits table indexing, `-ffast-math`-unsafe NaN comparison) already fixed there.

## Join types

```c
typedef enum { JOIN_INNER, JOIN_LEFT, JOIN_FULL } JoinHow;

DataFrame df_join(const DataFrame *left, const DataFrame *right, const char *on, JoinHow how);
```

- **`JOIN_INNER`** - only rows whose key exists on both sides.
- **`JOIN_LEFT`** - every row of `left`; a `left` row with no match gets NaN (numeric) / `"NA"` (string) in every column that came from `right`. This is also this project's left **outer** join - in SQL and in Polars, "left join" and "left outer join" name the same operation (Polars' own `how` values are exactly `inner`, `left`, `right`, `full`, `cross`, `semi`, `anti` - there is no separate "left" vs "left outer"), so there is only one entry point for it.
- **`JOIN_FULL`** - every row from both sides; whichever side has no match is NaN/`"NA"`, matching Polars' `"full"`.

`JOIN_RIGHT` (or "right outer join") has no separate entry point, by design: swap which `DataFrame` is `left`.

```c
/* right join of (orders, customers) on "customer_id": */
DataFrame out = df_join(&customers, &orders, "customer_id", JOIN_LEFT);
```

Every row that distinguishes "right" from "left" - which side's unmatched rows survive, which side's columns get the `_right` suffix on a name collision - is entirely a function of argument order, so a second code path would just be this one under a different name.

## What the output looks like

Columns: every column of `left`, in order, then every column of `right` **except** `on`, in order. A `right` column whose name collides with a `left` column (other than `on` itself) is renamed `<name>_right`, matching Polars' own default `suffix="_right"`. `on` itself appears exactly once, coalesced: `left`'s value where `left` has a matching (or any, for `JOIN_LEFT`/`JOIN_INNER`) row, `right`'s value only for a `JOIN_FULL` row that came from an unmatched `right` row (the only case where `left` contributes nothing).

Row order: every `left` row in its original order (fanning out to one output row per matching `right` row when the key repeats on `right`, and to zero rows for `JOIN_INNER` on no match), followed - for `JOIN_FULL` only - by every `right` row that never matched anything, in `right`'s original order.

A cell whose source row doesn't exist becomes NaN for a numeric column or `"NA"` for a string one. Numeric NaN-as-missing is new: `docs/FRAME_DOCUMENTATION.md`'s "A note on missing values" flagged it as a reasonable future enhancement once `MISNAN` existed to detect it reliably under `-ffast-math`, but no loader had used it - `JOIN_LEFT`/`JOIN_FULL` is the first caller with no alternative, since some output rows genuinely have no source row on one side. Check for it with `MISNAN`, never `==`/`isnan()` (see README's `-ffast-math` pitfall).

## Key matching

`on` must exist in both `left` and `right` with the **same column type** (`assert`ed - a contract violation, not a recoverable error, following this project's "fail loudly" convention). Both numeric and string keys are supported.

A numeric key that is NaN never matches anything, **including another NaN** - Polars' own default (`nulls_equal = false` in the Python API) - because this project's `DataFrame` had no missing-value sentinel for numeric data before this file, so a `NaN` key reaching `df_join` is already exactly the "no value here" case a join should never treat as matching. `JOIN_INNER`/`JOIN_LEFT` skip a NaN build-side key entirely rather than inserting it (nothing will ever probe-match it, so there's no reason to pay for the insert); `JOIN_FULL` still inserts it, since it needs to survive to the final drain step as an always-unmatched row - see `join_build_table`'s own comment for why this asymmetry is safe (`join_key_eq` already rejects any NaN-involving comparison, so a NaN key can never collide-match another bucket regardless of whether it was inserted for INNER/LEFT's sake or FULL's).

Duplicate keys fan out on both sides, ordinary SQL join semantics: a key appearing `m` times on the left and `n` times on the right contributes `m * n` rows to the result.

## Multithreading

Above `JOIN_PARALLEL_MIN_N` (200,000) combined rows (`left->r + right->r`), `df_join` builds the hash table over `right` in `n_threads` independent partitions and probes it with `left` split into `n_threads` contiguous row ranges, both via OpenMP - ported from Polars' own partitioned-build technique in the same `single_keys.rs` source the serial path is ported from (`build_tables`'s scan-and-reject-by-partition construction), matching the shape `frame/sql.h`'s GROUP BY `sql_build_groups_hash_1col_mt`/v8 already uses rather than inventing a new pattern. `n_threads` comes from `omp_get_max_threads()`; without `-fopenmp` (`_OPENMP` undefined) this always returns 1, and the partitioned code still runs, just correctly degenerate - one partition covering every row - the same reasoning `frame/sql.h`'s own `_mt` GROUP BY path already relies on to stay exercised by this project's default, non-`-fopenmp` `make test`. OpenMP itself is optional per README's Dependencies policy; see `frame/join.h`'s own `join_omp_*` wrapper functions and their comment for why they aren't just reusing `frame/sql.h`'s existing `omp_get_max_threads`/etc. stub names.

**A real, severe bug was found and fixed while building this.** The first working version of the partitioned build made every near-unique-key join dramatically *slower* under `-fopenmp`, not faster - a 1,000,000-row, near-unique-key `JOIN_INNER` took 27.4 seconds parallel against 456ms serial, a ~60x regression. Root cause, isolated by timing the build and probe phases separately and then reproducing the pathology in a standalone single-partition build: `join_key_hash`'s numeric path (`frame_dirty_hash_u64`) has decent entropy only in its top bits, by design - the same property `FrameHashTable`'s own doc in `frame/frame.h` documents and relies on for `frame_hash_table_index`'s top-bits table-slot extraction. Routing a key to a partition via `join_hash_to_partition` called directly on that same raw hash *also* reads the top bits (for a power-of-two thread count, exactly the top `log2(n_threads)` bits); once a partition was fixed, every key routed into it shared that same top-bit value, so `frame_hash_table_index`, still reading top bits from the identical hash, was left choosing a slot from far less usable entropy than the table's nominal capacity assumed. Measured directly: a standalone single-partition build restricted to the ~250,000 (of 1,000,000) near-unique keys that one top-bits-only partition selects took 12.3 seconds, against ~460ms for the entire non-partitioned, single-threaded build of all 1,000,000 rows.

The obvious first fix - partition by the hash's low bits instead, leaving the top bits free for `frame_hash_table_index` - is also wrong, and this too was measured rather than assumed: join keys are very often small non-negative integers stored as floats (row ids, counts, category codes), and `frame_canonical_f64_bits`/`f32_bits`'s raw IEEE754 bit pattern for a small integer has many trailing zero bits (few mantissa bits are needed to represent it exactly); multiplying by an odd constant (`frame_dirty_hash_u64`'s entire operation) cannot change a value's trailing-zero count, so the low bits inherit that same degeneracy. Measured on the identical 1,000,000-row case: routing by `h & (n_threads-1)` put every single row in partition 0, leaving the other three empty.

The actual fix, `join_mix64`: a full-avalanche 64-bit finalizer (Austin Appleby's `fmix64`, from MurmurHash3, public domain), applied to the hash before it is ever handed to `join_hash_to_partition` - never before `frame_hash_table_index`, which must keep reading `frame_dirty_hash_u64`'s own raw output to match `frame/sql.h`'s GROUP BY table exactly. `join_mix64`'s output bits are each a nonlinear function of every input bit, so extracting any range of them (top or bottom) carries none of the DirtyHash-specific "good only at the top, degenerate at the bottom for small integers" shape. Measured after the fix, on the identical case: a 4-way partition split of `{251478, 251121, 248451, 248950}` (essentially even) and 26.5ms to build the single partition that took 12.3 seconds before - and the full 1,000,000-row build+probe combined dropped from ~42 seconds (27.4s build + 15.3s probe) to ~154ms (77.6ms + 76.4ms), a genuine ~3x speedup over the 456ms serial baseline at 4 threads.

`tests/correctness/test_join.c`'s `test_partition_balance_regression` (checks the `join_hash_to_partition(join_mix64(...))` formula directly, runs unconditionally) and `test_partition_balance_via_real_build` (calls `join_build_partitions_mt` itself, only under a real `-fopenmp` build - see its own comment for why a hardcoded `n_threads > 1` isn't meaningful without one) guard against this recurring. Both check partition *balance*, not join output - see the Testing section below for why a correctness-only check could never have caught this bug in the first place.

**ThreadSanitizer note.** The synchronization design was verified by direct reasoning (each `#pragma omp parallel` block's mandatory implicit barrier at its closing brace guarantees full memory visibility across the sequential build-then-probe call, per the OpenMP standard; each thread ever *writes* only to its own array-indexed slot - `partitions[tid]`, `local[tid]` - never one another thread also writes; no bucket's `matched` flag is ever written during either parallel region, only in a later, deliberately serial pass - see `join_probe_mt`'s own comment) and by running the full test suite, including `test_parallel_dispatch_threshold`'s exact-output-set comparison against the independently-verified serial path, under a real `-fopenmp` build with genuine 4-thread execution (confirmed via `user` time running consistently above `real` time) - all passed. Running the same build under ThreadSanitizer on this machine reported data races at every one of the barrier-separated cross-thread reads described above; judged to be tool noise rather than a real race, for three reasons: (1) the reports are exactly the intended, barrier-protected cross-thread reads (a probe thread reading a partition another thread built, always after that partition's own build-region barrier), which the OpenMP memory model guarantees are synchronized; (2) several reports carry TSan's own "Location is stack of main thread" / "global `<null>`" annotations, a documented signature of TSan losing track of GCC `libgomp`'s thread-pool/stack reuse across sequential parallel regions rather than of an application-level race; (3) this machine's TSan setup needed a non-default workaround (`setarch -R`, disabling ASLR) merely to start without an unrelated "unexpected memory mapping" fatal error, indicating a generally fragile TSan environment here, not a clean instrument. Reported rather than hidden: a future contributor with a more reliable TSan/`libgomp` combination (or `clang`+`libomp`, not available on this machine) re-running this check is worth doing, not worth skipping just because this investigation didn't find a clean way to do it here.

## Testing

`tests/correctness/test_join.c` checks, in this order:

- **Known-output cases** for all three join types, including a duplicate key on `left` fanning out correctly, and that `JOIN_LEFT` with arguments swapped reproduces a directly-computed right join.
- **Four regression tests, one per real bug this implementation actually had**, each labeled `"regression: ..."` in its `puts()` header and each with a comment naming the bug, why it happened, and what assertion caught it - not just a test that happens to exercise the area:
  - `test_string_key` - `JOIN_FULL` with a string-typed `on` column. The numeric key-coalescing path (fall back to `right`'s value for a right-only row) was written first; the string path initially fell through to the generic "no source row -> `"NA"`" case even for the key column itself, so a right-only row showed `"NA"` instead of its own real key value. Caught by `assert(strcmp(oname[3], "dave") == 0)`.
  - `test_nan_key_never_matches` - `JOIN_FULL` with a NaN key on the build (`right`) side. `join_build_table` originally excluded every NaN-keyed row from the hash table unconditionally; correct for `JOIN_INNER`/`JOIN_LEFT` but wrong for `JOIN_FULL`, whose drain step only walks rows that made it into the table - a NaN-keyed `right` row was silently dropped instead of surviving as an unmatched row. Caught by `assert(full.r == 4)` (it returned 3 before the fix).
  - `test_partition_balance_regression` / `test_partition_balance_via_real_build` - the multithreaded build/probe's partition-selection bug (see the Multithreading section above for the full mechanism): partitioning and per-partition table-slot indexing were both drawing from the same "good" bits of the same hash, causing catastrophic clustering (a ~60x slowdown, not a wrong answer) for realistic near-unique integer-like keys. Caught by checking partition *balance* directly, not join output - a correctness-only test could never have failed from this bug, since `join_key_eq` doesn't care which partition a key landed in. Two tests, not one, because the first version of this check called the partition formula inline rather than through the real `join_build_partitions_mt`/`join_probe_mt` call sites, and kept passing even when the fix was reverted directly at those call sites - see `test_partition_balance_via_real_build`'s own comment for how that gap was found and closed.
- **Seven tests ported from Polars' own test suite** (tag `py-1.38.1`), each naming its source in a comment, adapted to this project's single-shared-`on`-name scope and its own NaN/`"NA"` missing-value markers in place of Polars' typed nulls: `test_join` (`py-polars/tests/unit/operations/test_join.py`) - string keys, per-column null counts across all three join types; `test_joins_with_duplicates` (`crates/polars/tests/it/core/joins.rs`) - heavy duplicate fan-out with exact row counts and per-column null counts, including that a right-only `JOIN_FULL` row leaves its `left`-only columns null and vice versa; `test_join_negative_integers` (same file) - negative numeric keys; `test_empty_outer_join_22206` and `test_join_coalesce_22498` (`test_join.py`) - `JOIN_FULL` against an empty counterpart, both directions; `test_empty_df_join` (`joins.rs`) - an empty probe (`left`) side gives zero rows for `JOIN_INNER`/`JOIN_LEFT`; `test_join_floats` (`joins.rs`) - a fractional (non-integer) floating-point key. One Polars assertion (`test_join`'s `joined["a"].null_count() == 1`) reflects `coalesce=False` being Polars' own default for `how="full"` when `left_on`/`right_on` are passed separately rather than a shared `on=` - a distinction `df_join` doesn't make, since it always coalesces - so that specific assertion is adapted rather than copied; the comment at that test's call site says so.
- **Adversarial cases:** the `_right` suffix on a genuine name collision; a NaN key never matching, not even another NaN, in both `JOIN_INNER` and `JOIN_FULL`; an empty `DataFrame` on either side; both contract violations (mismatched `on` types, a missing `on` column) aborting via fork + `SIGABRT`.
- **An independent reference:** randomized fuzzing (`srand(42)`) against a naive `O(n*m)` reference join, biased toward low key cardinality (heavy duplication, the fragile case for bucket fan-out) rather than well-conditioned uniform-random keys, plus single-row inputs. `make test-stress` adds larger, higher-cardinality cases specifically to force `FrameHashTable` through repeated growth.
- **The multithreaded dispatch itself:** `test_parallel_dispatch_threshold` crosses `JOIN_PARALLEL_MIN_N` (sizes 50,000 / 200,000 / 400,001, matching `frame/sql.h`'s own `test_sql.c` choice for its analogous threshold) and checks `join_probe`'s dispatched result against an explicit `join_probe_serial` call on the same input, as a *set* of `(left_row, right_row)` pairs rather than position-by-position - `JOIN_FULL`'s drained rows are only documented as ordered under a single, non-partitioned table, so exact order isn't part of the contract once there's more than one partition. Compares against `join_probe_serial` directly rather than the naive `O(n*m)` reference, which is not computationally feasible at `n=400,001` (this was tried; the process needed to be killed after not finishing in over two minutes).

Built and run under AddressSanitizer/UndefinedBehaviorSanitizer during development (this file is malloc-heavy: every bucket, every output row-index array, every thread-local buffer) - both with and without `-fopenmp`, since the parallel code path only actually runs threads under the latter.

## Benchmark results

`tests/performance/bench_join_compare.c` exposes `df_join` via ctypes (`c_join_load`, `c_join`, `c_join_close` - mirrors `bench_sql_compare.c`'s pattern exactly); `tests/performance/bench_join_compare.py` drives it against real Polars `.join()` on identical CSV data. Not part of `bench.sh`/`bench_report.txt`, the same reasoning as `bench_sql_compare.py` (an external-library comparison investigation, not the project's usual core-vs-one-Python-reference suite) - run directly:

```bash
python tests/performance/bench_join_compare.py
```

**Setup, held fixed throughout:** machine is a 4-core Intel Core i5-7400 @ 3.00GHz. Python: anaconda `python3.12`, `numpy` 2.4.4, `polars` 1.38.1. Both `left`/`right` are generated per case with `numpy.random.default_rng(11)`: a numeric key column via `rng.integers(0, cardinality, n)` cast to `float32` (or, for the string-key cases, the same integers formatted as `"id_<k>"`), plus one unrelated `float32` value column per side (`val` on `left`, `score` on `right`) via `rng.standard_normal`. Each `(size, cardinality, how)` combination is timed with the same `bench()` helper `bench_sql_compare.py` already uses: one untimed warm-up call, then 3 repeats each running the call in a tight loop for 1 wall-clock second, reporting the best (minimum) per-call time across the 3 repeats. Every case's row count is asserted equal between `df_join` and Polars' own `.join()` before timing - a correctness cross-check independent of `tests/correctness/test_join.c`, not just a speed measurement. `bench_join_compare.py` rebuilds `libjoincompare.so` via `make` by default (this project's default `CFLAGS`, no `-fopenmp`); set `JOIN_BENCH_SKIP_MAKE=1` to reuse an already-built `.so` instead - how the "parallel" column below was produced, from `libjoincompare.so` built by hand with `-fopenmp` added and run under `OMP_NUM_THREADS=4`.

**Cardinality is scaled with `n`, not held at a fixed low value.** A duplicate-heavy equi-join's output size grows as `n^2 / cardinality` (each of the `~cardinality` keys fans out `(n/cardinality) x (n/cardinality)` rows) - fixing `cardinality=100` while sweeping `n` up to 1,000,000 (an earlier version of this benchmark's first draft) reaches roughly 10 billion output rows and OOM-crashes the process; that failure mode is a benchmark-design bug, not a `df_join` bug (`tests/correctness/test_join.c`'s own growth-forcing `STRESS=1` cases stay at bounded cardinality for the same reason). Reported cardinalities keep output size in the tens-of-millions-of-rows range at most.

`serial` below is the single-threaded build (`JOIN_PARALLEL_MIN_N` never crossed, or crossed with `join_omp_max_threads()` stubbed to 1 - no `-fopenmp`); `parallel` is the identical binary rebuilt with `-fopenmp` and run with `OMP_NUM_THREADS=4`, **after** the partition-hash fix described in the Multithreading section above (the numbers this fix replaced - a single near-unique `JOIN_INNER` case that ran serial in 456ms and "parallel" in 27,352ms, a 60x regression - are not reproduced in full here; that investigation is the Multithreading section's own subject, not a benchmark result to report as this project's actual performance):

**What the numbers show, with a mechanism, not just the ratio:**

1. **Multithreading closes most of the near-unique-key gap, which is where it was worst.** `JOIN_INNER` at n=1,000,000 went from 7.70x to 2.86x serial-to-parallel; n=100,000 similarly went from 4.78x to 2.13x. Near-unique keys are close to a plain primary-key join with almost no bucket fan-out, so before multithreading the work was dominated by single-threaded construction and probing of `FrameHashTable` against Polars' own multi-threaded hash join - exactly the case parallelizing `df_join` targets first. The 2-3x remaining gap at 4 threads, not fully closed to 1.0x, is consistent with `df_join` still not implementing Polars' build-side-size heuristic (see Known limitations) and with per-row overhead that a real profiler run, not attempted here, would need to attribute precisely.
2. **Moderate-duplication cases now frequently beat Polars outright** (0.70x-0.79x at n=100,000 and n=1,000,000, `JOIN_INNER`/`JOIN_FULL`): before multithreading these were already close to parity single-threaded (see point 3 below, unchanged); adding genuine parallelism on top of an already-competitive single-threaded implementation pushes several cases past 1.0x.
3. **Heavy duplication (few, large buckets) got slightly *worse* under the parallel path** (1.38x->1.56x, 2.17x->2.44x at n=20,000/cardinality=50): the "scan every row, reject 3/4 of them" build strategy (see the Multithreading section) pays a flat ~4x hashing-work tax regardless of cardinality, and with only 50 real keys total, there's very little actual per-key work for 4-way parallelism to speed up - the tax shows up as pure overhead here. This case sits well below `JOIN_PARALLEL_MIN_N` territory in spirit even though its row count crosses the threshold; a future cardinality-aware (not just row-count-aware) dispatch condition could avoid paying this tax when it can't be recouped.
4. **String keys, right at the `JOIN_PARALLEL_MIN_N` boundary, got worse specifically at moderate duplication** (2.61x->2.92x, 3.01x->3.36x, 2.31x->2.63x, all at n=100,000+100,000=200,000 combined, exactly the threshold): string hashing (`join_key_hash`'s FNV-1a path) costs more per row than numeric hashing, so the same flat "scan and reject 4x" tax from point 3 costs proportionally more here too, and this case's total row count barely clears the threshold in the first place, leaving little room for 4-way parallelism to pay that tax back. The near-unique string case, by contrast, improved substantially (7.12x->2.64x) - duplication level and per-row hash cost interact, not just row count in isolation. A single row-count threshold clearly isn't the whole story; a future refinement is exactly the cardinality-aware dispatch point 3 already motivates, extended to account for per-row key cost too.
5. **`JOIN_FULL`'s ratio is still the best of the three join types at nearly every size**, both before and after multithreading, often at or below 1.0x: `JOIN_FULL` is the one join type where Polars must additionally track which build-side rows were never matched and drain them at the end (`probe_outer`'s tracked-bucket approach - the same mechanism `df_join` itself ports, see the Overview), work `INNER`/`LEFT` skip entirely on both sides.

## Known limitations and future work

- **Single shared column name only.** `on` must name the same column in both frames; there is no `left_on`/`right_on` for joining differently-named columns, and no multi-column composite key. Matches the current scope of `frame/sql.h`'s own grammar (no `JOIN` keyword yet either - see `docs/SQL_DOCUMENTATION.md`'s known-limitations list), rather than a deliberately narrower one.
- **No build-side-size heuristic.** `df_join` always builds over `right`, whether or not it's the smaller side; Polars picks whichever relation is smaller and swaps the output tuple order back after. Not implemented, in serial or multithreaded form - see the Overview and Multithreading sections above. Measured, not just stated: the asymmetric-size benchmark cases (`n_left=1,000,000`/`n_right=1,000` vs. the reverse, in the script's own output) show a real, size-dependent cost specifically from always building over whichever DataFrame happens to be passed as `right`.
- **The `JOIN_PARALLEL_MIN_N` dispatch is row-count-only, not cardinality- or key-type-aware.** The multithreaded build's "scan every row, reject the ones not in this partition" strategy (see the Multithreading section) pays a flat ~`n_threads`x hashing-work tax regardless of how many distinct keys actually exist to parallelize over, and a string key costs more per hash than a numeric one. The Benchmark results section's heavy-duplication and string-at-the-threshold rows measure this directly: both got measurably *worse* under the parallel path than the serial one, because there wasn't enough real per-key work to recoup the flat tax. A future dispatch condition that also accounts for estimated cardinality and key type, not row count alone, would fix this; not attempted here since it requires a cardinality estimate cheaper than just doing the build.
- **String-typed keys are proportionally slower than numeric ones.** `join_key_hash`/`join_key_eq`'s string paths are `O(key length)` (FNV-1a, `strcmp`) against the numeric path's `O(1)` canonicalized-bits compare - see the Benchmark results section's string-key rows. Not addressed here; a future fix would likely mean interning/hashing string keys once up front rather than re-hashing/re-comparing raw bytes per probe.
- **The missing values this file writes are the only ones the statistics layer ever sees.** A `JOIN_LEFT`/`JOIN_FULL` output row with no match carries a genuine `NaN` in its numeric columns, and `df_join` is the only route by which a `NaN` gets into a numeric column at all in this project — a loader types an `NA`-bearing column as strings instead. Everything above `frame/` now handles that by one rule: the accumulating statistics let the `NaN` through to the answer, and everything that sorts or returns a verdict asserts. That rule exists because of this function, and `tests/integration/join_missing_values.c` checks it against real join output; see `docs/FRAME_DOCUMENTATION.md`'s note on missing values for the table. What is still missing is the other half — there is no `df_dropna`, so dropping the unmatched rows before handing a column onward is the caller's own loop, and `mat_all_finite` is how they know whether they need one.
- **No `semi`/`anti`/`cross` joins.** Only the three join types actually requested exist. Polars' `semi` (left rows with a match, no right columns) and `anti` (left rows with no match) are easy additions on top of the existing probe loop if needed later; `cross` (Cartesian product) needs no hash table at all and would be its own, much simpler function.
